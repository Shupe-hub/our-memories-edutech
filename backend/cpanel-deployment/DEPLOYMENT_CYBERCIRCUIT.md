# CyberCircuit cPanel deployment preparation

> **Archived rollback material.** The active preparation path is Railway with PostgreSQL; see [../DEPLOYMENT_RAILWAY.md](../DEPLOYMENT_RAILWAY.md). This cPanel/MariaDB source tree is retained to preserve the CyberCircuit rollback option and is not synchronized with the Railway application. Its lockfile still uses Prisma 6 and the registry audit reports four high advisories through Prisma's config dependencies. Do not use it for a fresh installation without a separately reviewed dependency update and verification. No production files or services were changed here.

This guide records the earlier hosting preparation only. It does not describe the current Railway application configuration.

## Compatibility and migration status

- PostgreSQL remains the default application database (`DATABASE_PROVIDER=postgresql`) and the canonical schema remains `prisma/schema.prisma`.
- A separate MySQL-provider Prisma schema and initial SQL baseline are under `prisma/mariadb/`. Prisma uses provider `mysql` for MariaDB.
- PostgreSQL UUID columns become UUID-formatted strings (`VARCHAR`); PostgreSQL `String[]` fields are represented as MariaDB JSON arrays. JSON, enum, Decimal(10,2), and millisecond DateTime fields are retained. Long text fields and email lengths were sized explicitly to avoid MySQL's default `VARCHAR(191)` for user-entered content.
- MariaDB's `JSON` type is an alias for `LONGTEXT` with JSON validation, so JSON storage/filtering and default behavior must be verified on the exact MariaDB 10.11 staging version.
- The generated MariaDB baseline uses `utf8mb4_unicode_ci`; its case-insensitive string searches rely on that collation, and institution alias lookup uses the MySQL JSON `array_contains` form. The transfer preflight checks case/accent-insensitive collisions for unique text fields and values exceeding bounded database fields. Confirm MariaDB's actual collation behavior on staging before any import.
- Prisma validation and generated migration SQL are preparation checks only. The initial MariaDB migration has not been applied and the transfer script has not been run against a database. The schema and data mapping still require a staging MariaDB 10.11 compatibility run, data-volume timing, and end-to-end verification before production approval.
- Existing PostgreSQL migrations are historical and must remain in `prisma/migrations/`. Do not point MariaDB at that directory.

## Versions

CyberCircuit confirmed Node.js 22.23.5. The package engine range `>=22.12 <23` accepts that version, and Prisma ORM v6 supports Node 22.11+ according to its upgrade guide. The workspace's available runtime is Node 22.14.0, so Node 22.23.5 itself and the CyberCircuit Linux image have not been exercised here. Prisma 6.19.3 declares Node `>=18.18`; Prisma Client generation and the backend tests passed locally on Node 22.14.0. Prisma 6 support ended on 19 November 2026; schedule a Prisma upgrade to continue receiving support.

MariaDB 10.11.19 uses Prisma's MySQL connector. Prisma's MySQL connector supports MariaDB, but server-specific behavior such as JSON defaults, collation and unique-key semantics must be confirmed on a disposable staging database first.

Do not extract a second `cpanel-deployment/` directory. Confirm `server.js` and `package.json` are directly in `our-memories-backend/`.
3. In the Node.js app environment UI, add the values listed below. Do not upload `.env.example` renamed to `.env`; it contains placeholders only. Do not set `PORT` manually if cPanel supplies it.
4. Use the app's **Run NPM Install** / **Enable Dependencies** control. This installs from the included lockfile. The install `postinstall` runs `prisma generate --schema prisma/mariadb/schema.prisma`; Prisma CLI is in production dependencies so production-mode npm install does not omit it. This generation step does not connect to MariaDB and does not apply migrations.
5. If the cPanel UI does not install dependencies or does not run package lifecycle scripts, use Terminal/SSH or request CyberCircuit to run, from the application root, `npm ci` followed by `npm run prisma:validate:mariadb` and `npm run prisma:generate:mariadb`. These are the only dependency/schema-generation operations required for installation. Linux dependency installation (including bcrypt's native binary and Prisma's engine libraries) has not been tested from this Windows workspace; let the cPanel install report its actual result.
6. Create a persistent private storage directory such as `/home/<CPANEL_USER>/private/our-memories-documents` using File Manager or ask the host. Grant the Node application user write/read access. Set `APPLICATION_STORAGE_PATH` to this absolute path; the backend rejects any path under `public_html`.
7. Start or restart the application from **Setup Node.js App** after its database schema exists and all environment variables are configured. Do not start it against an unmigrated database; startup initialization requires the MariaDB tables. Use the same UI's restart/redeploy action after environment changes.
8. Check `https://api.ourmemoriesedutech.co.za/api/health`. Expect HTTP 200 with `status: ready` only after the MariaDB baseline is separately applied, connectivity succeeds, and private storage/startup checks pass. HTTP 503 means the API is listening but its readiness conditions are not met. No health request was sent during package preparation.

## MariaDB migration and transfer procedure

These are operator commands for a future, approved window; none have been executed against the hosting database:

1. Take and verify a restorable PostgreSQL backup and a private-document backup. Keep PostgreSQL and its files intact.
2. Create a disposable MariaDB 10.11 staging database with the same character set/collation as production. Never use the production target for initial rehearsal.
3. Run `npm ci`, `npm run prisma:audit:mariadb`, `npm run prisma:validate:mariadb`, and `npm run prisma:generate:mariadb`.
4. On staging only, review the generated baseline and run `npm run prisma:deploy:mariadb` with `DATABASE_URL` set to staging. Confirm expected tables, indexes, foreign keys, JSON defaults and enum behavior.
5. Exercise the application against staging using synthetic accounts and documents only. Cover registration/login, student and administrator authorization, password reset through a controlled email sink, application enquiry submission/update, institution and bursary workflows, document metadata/ownership/associations/download permissions, notifications, deadline reminders, institution search, admin management, and API health. Do not copy local or production student records for this test.
6. For a production transfer, schedule maintenance/read-only mode so source data cannot change during the copy. Provide `SOURCE_DATABASE_URL`, point `DATABASE_URL` at the empty MariaDB target, and set absolute source/target private storage paths. First run `npm run transfer:dry-run` and inspect every count/preflight result.
7. Execute the transfer only after explicit approval and a verified backup. It requires `--execute`, `--confirm-data-transfer`, `--confirm-target=<host>/<database>`, and `TRANSFER_TARGET_ENV=staging|production`. Production additionally requires `--confirm-production-transfer`. The script refuses if any of its 24 application tables already contain rows and refuses to overwrite document files. It commits each model's batches in one transaction, defers self-referential document replacement links until all documents exist, and verifies row counts plus deterministic SHA-256 record checksums after import. Document files are copied first with exclusive create and per-file SHA-256 verification. Therefore file copies and database rows cannot be one atomic transaction: after interruption, target rows/files may be partial and must be discarded/recreated by the operator using the approved staging/backup procedure; the script intentionally never deletes or resets anything.
8. Verify all 24 model counts/checksums, foreign-key consistency, collation collisions, document checksums/downloads, password login and reset flows, application behavior, email and logs. Keep the PostgreSQL source and document backup untouched through the agreed rollback period.
9. Change `DATABASE_PROVIDER=mysql` only for the approved MariaDB application deployment, then route production traffic after sign-off. Preserve the original PostgreSQL schema and migrations.

Never run `prisma migrate reset`, `db push`, or migration commands against the existing PostgreSQL database as part of this preparation. The MariaDB migration is a separate baseline, not an alteration of the PostgreSQL migration chain.

## Disposable MariaDB 10.11 staging setup

This repository's local environment currently has PostgreSQL active and a MySQL 8 Windows service, but no MariaDB server. Do not use that MySQL 8 service or the CyberCircuit production database for this rehearsal. Ask CyberCircuit to provide a disposable MariaDB 10.11.19 staging instance/database, isolated from production if their plan supports it. If they only offer a separate database on the production server, confirm with CyberCircuit that the staging database is separate, disposable, version-compatible, and isolated by its own database user before proceeding.

In cPanel, use **Database Wizard** (or **MySQL Databases**) to create a new database such as `ourmemor_ome_stage` and a new user such as `ourmemor_ome_stage_user`. cPanel may prepend the account prefix, so record the exact resulting names. Grant that user access only to the staging database. Do not select or reuse `ourmemor_edutech` or `ourmemor_edutech_user`. Ask the host to confirm the server reports MariaDB 10.11.x (ideally the same 10.11.19 patch version), `utf8mb4` character set, and `utf8mb4_unicode_ci` collation. cPanel documents that its database wizard creates a database and user and assigns the user's privileges to that database ([cPanel Database Wizard](https://docs.cpanel.net/cpanel/databases/mysql-database-wizard/)).

Keep the staging URL in a password manager or hosting environment settings, not a committed file. For a local Windows rehearsal, open a dedicated PowerShell window in `backend` and temporarily override only that process environment; replace the example host, prefixed DB/user names, and password with the staging values. URL-encode reserved characters in the password:

```powershell
$previousDatabaseUrl = $env:DATABASE_URL
try {
  $env:DATABASE_URL = 'mysql://ourmemor_ome_stage_user:<URL_ENCODED_PASSWORD>@<STAGING_HOST>:3306/ourmemor_ome_stage'
  npm run prisma:audit:mariadb
  if ($LASTEXITCODE -ne 0) { throw 'MariaDB schema audit failed' }
  npm run prisma:validate:mariadb
  if ($LASTEXITCODE -ne 0) { throw 'MariaDB schema validation failed' }
  npm run prisma:generate:mariadb
  if ($LASTEXITCODE -ne 0) { throw 'MariaDB Client generation failed' }
  npm run prisma:deploy:mariadb
  if ($LASTEXITCODE -ne 0) { throw 'MariaDB staging migration failed' }
} finally {
  if ($null -eq $previousDatabaseUrl) {
    Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
  } else {
    $env:DATABASE_URL = $previousDatabaseUrl
  }
}
```

Before running `prisma:deploy:mariadb`, verify the URL host/database name against the host's staging confirmation and verify the DB account has access only to that staging database. `migrate deploy` applies migrations from the selected schema's migration directory; the command above selects only `prisma/mariadb/schema.prisma` ([Prisma ORM 6 migrate deploy](https://www.prisma.io/docs/orm/v6/prisma-client/deployment/deploy-database-changes-with-prisma-migrate)). Do not put staging or production credentials in `backend/.env`; the temporary shell override leaves the PostgreSQL `.env` and runtime default unchanged.

After applying the baseline, inspect the staging database with the host's SQL console or a staging-only SQL client: expect 24 application tables plus Prisma's `_prisma_migrations` table, 46 foreign keys, 24 model primary keys, and 45 model indexes/unique constraints. Then run CRUD, relationship, JSON, collation/unique-collision, and full workflow tests with synthetic values only. Use a controlled email sink or leave Resend unconfigured; password-reset email delivery must not point at real recipients. Use synthetic PDF/JPEG/PNG test files in a private staging storage directory outside `public_html`; verify authenticated owner/admin downloads and rejected cross-user access. Record each test result and clean up only through the disposable staging environment's approved teardown process.

No staging server URL or credentials were available during this preparation. Therefore this guide has not applied the migration, checked live MariaDB version/catalogs, run staging CRUD or application workflows, or moved test files. Those steps remain pending until the isolated staging environment is available; production remains untouched.

## Backend and domain

Configure `api.ourmemoriesedutech.co.za` as the cPanel Node application URL and issue SSL for it. Configure `ourmemoriesedutech.co.za` and `www.ourmemoriesedutech.co.za` to serve the frontend over HTTPS. The server accepts only origins listed in `CORS_ORIGINS`; browser API requests include credentials. Authentication cookies are HttpOnly, `SameSite=Lax`, and become `Secure` when `NODE_ENV=production`. Because the two hosts are same-site subdomains, a shared cookie domain is not required for the current host-only cookie design.

The unauthenticated `/api/health` endpoint returns 503 until the database and private storage setup complete, then 200. During startup, other `/api` routes return a controlled 503. Check the Node app logs for a safe error code if health remains unavailable; never add database passwords, tokens, or full error objects to logs.

## Resend and documents

Verify the sender domain with Resend and use the approved sender address in `EMAIL_FROM`. Set `RESEND_API_KEY`, `EMAIL_REPLY_TO`, and `APP_PUBLIC_URL` in the backend environment. Email transport failures are logged without returning a stack trace or rolling back successful account/application writes; password reset returns a generic response and removes an unsent reset token where possible.

Document storage must be persistent and outside `public_html`. The application validates PDF/JPEG/PNG signatures as well as extensions and enforces the configured byte limit. Download routes retain authentication and ownership/administrator checks. Back up both private files and their database metadata; restoring only one side leaves document references unusable. Do not delete the current upload directory during deployment.

## Backup, restore, and troubleshooting

- Before each approved schema/import change, export the MariaDB database and private document directory to separate protected backups and verify a restore into a disposable location.
- For rollback, route traffic back to the retained PostgreSQL-backed application and its matching private document storage. Do not point the PostgreSQL app at MariaDB or reverse an import by deleting source records.
- `npm run prisma:validate:mariadb` validates schema syntax without connecting to MariaDB. `npm run transfer:dry-run` requires both DB connections and is read-only, but still displays host/database names and row counts; run it only in a protected terminal.
- For a staging-only import after creating and validating an empty MariaDB staging schema, set `TRANSFER_TARGET_ENV=staging`, then call `npm run transfer:execute -- --confirm-data-transfer --confirm-target=<staging-host>/<staging-database>`. The script also adds `--execute` through the npm script. Never set the production environment flag or confirmation without a separate explicit approval.
- If `/api/health` is 503, inspect cPanel environment variables, assigned `PORT`, DB host/user grants, schema migration status and private storage permissions. A proxy 502/connection reset usually means the cPanel Node process is stopped or listening on the wrong port; use cPanel's assigned port and restart the app.
- For browser CORS/auth issues, confirm HTTPS on both hosts, exact origins in `CORS_ORIGINS`, frontend `VITE_API_URL`, and that requests include credentials. Do not loosen the origin list to `*`.
- Check Resend readiness from the administrator email settings; never print the API key. If delivery fails, confirm key, sender-domain verification, `EMAIL_FROM`, and outbound connectivity.
